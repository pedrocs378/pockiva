The real-socket integration test was run repeatedly with `--all-features`. It starts an actual loopback HTTP/WebSocket server and drives the real desktop manager and emulator worker into a recording core. Each observed run completed in approximately 1.36–1.38 seconds.

The test proves:

- invalid-token and second-controller rejection;
- keyboard source `1` and remote source `2` reaching the core independently;
- exactly 200 remote state applications, a retained latency window of 128 samples, and loopback p95 below 100 ms;
- pause, resume, restart, and ROM replacement preserving the remote session;
- abrupt transport loss clearing only source `2` while the runtime stays running;
- reconnect with the same unexpired token followed by a complete `state-sync`;
- explicit end clearing source `2`, retaining source `1`, stopping the listener, and invalidating the old session URL.

The integration ROM is a synthetic temporary byte fixture generated by the test, removed afterward, and is not compatibility evidence.

1. On a native Windows x64 machine with MSVC Build Tools, run the network and desktop tests, build the Tauri `.exe`, and verify private-network firewall behavior, reconnect, one-controller rejection, explicit end, and process-exit listener cleanup.
2. Run an extended 15-minute real-device LAN telemetry session and record device/browser versions and LAN p95. The functional phone/ROM flow was accepted by the user, but this additional telemetry was not recorded.

If native Windows validation is performed later, Windows Firewall should be allowed only for the private network. A cross-compile or macOS target check does not replace that optional native evidence.
